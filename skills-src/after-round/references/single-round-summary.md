# 单场面试归纳参考

用于一整场面试材料的转录、整理、复盘、归档和复盘追问。涉及音视频转录、飞书 OAuth、飞书文档写入、多维表格归档或追问追加的具体实现时，同时读取 [transcription-feishu-archive.md](transcription-feishu-archive.md)。

## 触发场景

- 用户说“面试复盘”“帮我整理这场面试”“after round”“面完复盘”“技术面复盘”。
- 用户提供音频或视频路径：`.wav`、`.m4a`、`.mp3`、`.mp4`。
- 用户提供 PDF、DOCX、Markdown、TXT、聊天记录或粘贴的面试转录。
- 用户要求保存到本地 Markdown、飞书文档或多维表格。
- 用户要求分析程序员面试中的项目追问、八股、手撕代码、系统设计、反问。

## 输入处理

- 音频或视频：先检查同目录是否存在同名 `.txt`。存在则跳过转录；不存在则使用本地转录工具生成 `.txt`。
- 已有转录或文档：直接读取全文并进入整理。
- 多文件：按文件名时间戳、开场白、道别语和上下文语义排序；排序不确定时让用户确认。
- 零散回忆：可以复盘，但所有结论标注“基于用户回忆，证据不完整”。

音视频转录优先级：

- 转录前必须先激活 after_round 专用虚拟环境，默认 `~/.codex/venvs/after-round`；不存在则创建，Python 转录依赖只安装到该环境。
- Apple Silicon Mac：优先 `mlx-whisper`。
- 其他平台：优先 `faster-whisper`。
- 依赖缺失时，不阻塞复盘；提示用户提供转录文本或安装依赖。

## 信息收集

开始整理前尽量一次性收集，不要反复打断：

- 保存方式：本地 Markdown 或飞书文档。
- 日期、公司名、岗位名、面试轮次。
- 面试官姓名和面试时长，均可选。
- 候选人简历：文件路径、文本，或至少项目经历摘要。
- 用户特别关注点：项目追问、八股、手撕代码、某个具体问题、二面准备等。

如果用户选择飞书，先检查飞书配置是否存在且有效。飞书配置、OAuth、文档写入和多维表格写入流程见 `transcription-feishu-archive.md`。

## 简历处理

程序员面试复盘默认需要简历上下文。处理前按顺序尝试：

1. 用户给了简历路径或文本时，读取并提取结构化信息。
2. 面试材料同目录附近有明显简历文件名，如 `resume`、`cv`、`简历` 时，可提示用户确认后读取。
3. 用户不提供简历时继续复盘，但“简历匹配度”部分必须说明限制。

从简历中提取：

- 目标岗位、年限、主语言、技术栈。
- 每个项目的业务背景、候选人职责、技术方案、难点、指标、产出。
- 高风险关键词：高并发、缓存、消息队列、分布式事务、索引优化、JVM、Go runtime、React/Vue、Kubernetes、微服务、RAG、向量数据库、模型评测等。
- 简历声称和面试回答之间的风险：项目贡献边界不清、指标不自洽、只会说用了什么但说不清为什么。

## 三份固定产物

无论本地保存还是飞书保存，都默认生成三份内容：

1. 完整对话：按时间顺序保留全程对话，发言人清晰。
2. 问答整理：按问题分组，程序员面试优先按五个环节分组。
3. 面试总评：指出表现、风险、没答好的问题和下次准备动作。

本地保存时统一写入源文件同目录的 `outputs/` 分类子目录；创建文件前必须先创建这些目录：

- `outputs/完整对话/{公司}-{岗位}-{轮次}-完整对话.md`
- `outputs/问答整理/{公司}-{岗位}-{轮次}-问答整理.md`
- `outputs/面评总结/{公司}-{岗位}-{轮次}-面试总评.md`
- `outputs/飞书归档状态/{公司}-{岗位}-{轮次}-飞书归档状态.md`
- `outputs/飞书归档结果/{公司}-{岗位}-{轮次}-飞书归档结果.json`

若飞书归档尚未执行但需要保存待办状态，将待办 Markdown 写入 `outputs/飞书归档状态/`，文件名用 `{公司}-{岗位}-{轮次}-飞书归档待执行.md`。

飞书保存时创建三份文档并返回链接；面试类型还要更新多维表格。若飞书配置缺失或 API 失败，降级为本地 Markdown，不能丢失复盘结果。

完成后必须在对话框中完整输出“面试总评”，不能只说已保存。

## 完整对话

- 识别发言人：提问、追问、反馈的是面试官；介绍项目、回答问题、写题思路的是候选人。
- 保留原始内容，不随意删减。
- 发言人标签统一为“面试官”和“我”。
- 转录不清楚的地方保留“不确定”标记，不编造。

## 问答整理

每组问答要包含：

- 问题标题：用一句话概括核心话题。
- 面试官问题：尽量还原原问题。
- 我的回答：整理候选人实际回答。
- 追问：若有追问，合并在同一组或连续编号。
- 环节归类：项目介绍、项目细节、基础知识、做题、反问、其他。

候选人的反问也必须进入问答整理，不能漏掉。

## 程序员面试五段拆解

技术岗位面试必须按下面五段复盘。没有出现的环节写“本场未出现”，不要强行编造。

### 1. 项目自我介绍

判断候选人是否讲清楚：

- 业务背景。
- 个人角色和职责边界。
- 技术栈和核心方案。
- 关键难点、权衡和结果指标。
- 为什么这个项目能证明自己适合目标岗位。

输出一版 60 秒项目介绍和一版 2 分钟项目介绍。必须贴合简历项目，不要写泛泛模板。

### 2. 项目细节追问

识别所有围绕简历项目、自我介绍和项目经历展开的问题。每个问题分析：

- 面试官问了什么。
- 实际考察点：真实性、架构能力、工程权衡、问题定位、数据意识、协作边界、owner 意识。
- 候选人答了什么。
- 回答缺了什么：背景、规模、方案、权衡、结果、复盘。
- 是否暴露风险：只说用了什么、没说为什么；只说结果、没说过程；贡献边界不清；指标不可信。

明显没答好的项目问题，要补一版更好的回答。优先用“背景-问题-方案-权衡-结果-反思”结构。

### 3. 基础知识和八股

识别项目延伸出的基础题和纯八股题，按主题分类：

- 语言和运行时：Java、Go、Python、JavaScript、TypeScript、C++ 等。
- 计算机基础：操作系统、网络、数据库、数据结构、复杂度。
- 工程中间件：Redis、MySQL、Kafka、MQ、RPC、缓存、搜索、对象存储。
- 分布式和架构：一致性、限流、熔断、幂等、事务、CAP、微服务、可观测性。
- 前端或客户端：浏览器、渲染、状态管理、性能、包体、稳定性。
- AI/数据工程：RAG、向量数据库、模型调用、评测、训练数据、推理性能。

每个问题都要判断回答是否准确、是否只背定义、是否能结合项目解释。答错时给出正确要点和一版面试可讲的简洁回答。

### 4. 做题、手撕代码或系统设计

识别算法题、SQL 题、并发题、代码补全、debug、系统设计或白板设计。每题输出：

- 题目复原：题意、输入输出、约束、边界条件。
- 候选人思路：暴力解、优化、数据结构选择、复杂度。
- 执行表现：是否澄清、是否写出代码、是否处理边界、是否自测和 debug。
- 最终状态：AC、部分完成、卡住、口述、未写完、无法确认。
- 问题定位：思路、实现、复杂度、边界、沟通或时间管理。
- 改进方案：标准思路、关键代码骨架、复杂度、补练题型。

没有完整代码时，不要凭空补候选人代码；可以给出推荐解法和下次答题步骤。

### 5. 反问环节

判断候选人是否问了：

- 团队业务和当前技术挑战。
- 岗位预期和入职后衡量标准。
- 技术栈、工程质量、协作方式。
- 面试官对本场表现的反馈。

指出不合适的反问，并给出 3-5 个更贴合公司、岗位和轮次的反问问题。

## 面试总评结构

总评必须直接指出问题，避免只写“整体不错”。按以下结构输出：

### 一句话结论

一句话说明本场主要结果倾向和最大风险。

### 面试问题总览

按五个环节列出面试官问了什么，每个问题一句话概括并编号。

### 简历匹配度

对照简历判断：

- 哪些简历项目被问到。
- 回答是否撑得住简历描述。
- 哪些简历关键词下次前必须补强。
- 哪些项目卖点没有讲出来。

简历缺失时，本节改为“简历缺失导致的复盘限制”。

### 分环节复盘

每个出现过的环节按固定结构：

```markdown
#### 环节名称

- 问了什么：
- 候选人回答摘要：
- 答得好的地方：
- 没答好的地方：
- 面试官可能扣分点：
- 下次更好的回答：
- 下次准备动作：
```

### 回答不够好的问题清单

必须列出 3-8 个最需要修复的问题。每项包含：

- 原问题。
- 原回答的问题。
- 为什么会扣分。
- 更好的回答方向。
- 复习材料或练习建议。

优先挑会影响结果的问题，不要纠结语气小瑕疵。

### 手撕代码专项复盘

有做题时单独输出；没有做题则写“本场未出现”。有做题时至少包含：

- 题目复原。
- 标准解法。
- 复杂度。
- 候选人卡点。
- 下次答题 SOP：澄清约束、举例、暴力、优化、编码、自测、复杂度总结。

### 下一轮准备清单

输出可执行计划：

- 24 小时内必须补的 3 件事。
- 下一场面试前要重写的项目讲法。
- 需要背熟但要结合项目讲的基础题。
- 需要补练的算法或系统设计题型。
- 推荐反问问题。

## 飞书和多维表格

用户选择飞书时，按 `transcription-feishu-archive.md` 中的流程：

- 检查 `~/.codex/feishu_config.json`。
- 获取并缓存 user access token。
- 创建三份飞书文档。
- 批量写入文档块。
- 面试类型更新多维表格。
- 输出文档链接和总评。

关键约束：

- token 获取后在同一脚本中继续创建文档和写 bitable，不要中断等待。
- 批量写入每批不超过 20 块。
- 不使用 `text_color`。
- 多维表格每次新建记录，不覆盖旧记录。

## 复盘追问模式

完成后询问用户是否开启复盘追问模式。开启后：

- 用户继续问本场面试相关问题时，回答必须结合本场转录和简历。
- 用户说“存”“保存”“存进去”“存到飞书”时，将开启模式后的新问答追加到总评文档的“复盘追问”章节。
- 本地模式追加到本地总评 Markdown；飞书模式追加到总评文档。
- 多场面试时，用户必须指定保存到哪一场；如果用户说“都存”，分别追加。

## 质量原则

- 具体优先：评价必须落到具体问答，不空泛安慰。
- 简历对齐：判断回答质量时考虑简历声称了什么。
- 不编造：转录、简历或代码缺失时明确说明缺口。
- 可执行：每个薄弱点都给出下一步怎么补。
- 面向下一场：复盘目标是让候选人知道下次哪些问题必须答得更好。
